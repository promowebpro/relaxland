# RelaxLand Можайский --- SPEC для разработки

**Статус:** исходная спецификация для старта проекта в Codex\
**Цель:** реализовать публичный сайт по утвержденным макетам на Laravel
с готовой административной панелью и отдельным интерактивным модулем
генплана.

> Важно: макеты являются источником истины для визуальной части. Не
> «улучшать» дизайн самостоятельно и не заменять композицию готовыми
> UI-шаблонами. Админка не определяет внешний вид публичного сайта.

------------------------------------------------------------------------

## 1. Технологическая основа

### Backend

-   Laravel.
-   MySQL 8+.
-   Очереди и кэш предусмотреть архитектурно; Redis не обязателен для
    первого релиза.
-   Хранение файлов через Laravel Storage с возможностью позже
    переключить диск на S3-совместимое хранилище.

### Frontend

-   Blade как основной серверный рендеринг.
-   Vite.
-   CSS: Tailwind CSS либо собственный слой CSS поверх Tailwind ---
    выбрать один подход и придерживаться его во всем проекте.
-   JavaScript использовать точечно для интерактивных элементов.
-   Не строить SPA без отдельной необходимости.
-   Анимации и интерактив должны деградировать корректно без нарушения
    основной навигации и контента.

### Административная панель

-   Filament.
-   Публичный frontend полностью отделен визуально от Filament.
-   Админка размещается в `/admin`.
-   Для ролей и разрешений: Spatie Laravel Permission.
-   Для интеграции разрешений с Filament допустимо использовать Filament
    Shield, если совместимость подтверждена перед установкой.
-   Все критичные проверки доступа дополнительно обеспечиваются Laravel
    Policies/Gates, а не только скрытием кнопок интерфейса.

------------------------------------------------------------------------

## 2. Основные принципы

1.  Макеты --- источник истины для frontend.
2.  Повторяющиеся элементы оформлять компонентами.
3.  Не превращать сайт в универсальный page builder.
4.  Контент должен редактироваться там, где это реально требуется
    заказчику.
5.  Композиция ключевых страниц фиксируется кодом согласно дизайну.
6.  Генплан проектировать как отдельный доменный модуль.
7.  Статусы участков и данные генплана не должны быть захардкожены в
    шаблонах.
8.  SEO-поля должны редактироваться из админки.
9.  Изображения должны иметь desktop/mobile варианты там, где этого
    требует дизайн.
10. Все формы должны сохранять заявки в БД, а не только отправлять
    email.

# 12. Генплан --- отдельный доменный модуль

Генплан является наиболее сложной частью проекта и не должен быть
реализован как статичная картинка с набором захардкоженных `div`.

Текущий дизайн показывает как минимум:

1.  Дефолтный вид при первом открытии.
2.  3D-план.
3.  3D-план с отображением объектов/мест.
4.  2D-план.
5.  Выбор квартала.
6.  Переход к сценарию выбора участка.
7.  Окружение на карте.
8.  Desktop и mobile состояния.
9.  Переключение между режимами «Генплан / Окружение».
10. Переключение 2D / 3D.

# 14. Координаты и SVG

Для объектов поверх генплана **не хранить пиксельные координаты
конкретного размера экрана**.

Допустимые подходы: 1. SVG `viewBox` с координатами относительно
исходного изображения. 2. Нормализованные координаты 0..1.

Для кварталов и участков предпочтительно SVG polygon/path overlay.

Это позволяет: - масштабировать план; - сохранять кликабельные зоны; -
подсвечивать кварталы; - показывать статусы; - использовать одну
геометрию на разных разрешениях; - реализовать hover/focus/click; - не
привязываться к конкретной ширине изображения.

# 15. Сценарий генплана

## Уровень 1 --- обзор

Показывается поселок целиком.

Пользователь может: - переключить 2D/3D; - открыть инфраструктурную
точку; - выбрать квартал; - перейти в «Окружение».

## Уровень 2 --- квартал

После выбора квартала: - подсветить квартал; - показать карточку; -
название/номер; - краткая информация; - CTA «Выбрать участок».

## Уровень 3 --- участки

Архитектурно предусмотреть даже при отсутствии окончательного макета: -
отображение участков выбранного квартала; - статус; - номер; -
площадь; - цена; - карточка участка; - CTA заявки.

Не реализовывать окончательный UI уровня 3 без макета, но БД/API не
должны требовать переделки для его добавления.

------------------------------------------------------------------------

# 16. Окружение

Режим «Окружение» --- отдельный слой интерфейса с картой.

Категории предусмотреть конфигурируемыми. Примеры из текущего
концепта: - образование; - магазины; - медицина; - еда; - развлечения; -
спорт; - транспорт.

Точки должны управляться из Filament.

Конкретный картографический провайдер выбрать на этапе реализации после
проверки требований, лицензирования, стоимости и доступности для целевой
аудитории. Не связывать доменную модель `SurroundingPlace` с API
конкретного провайдера.

------------------------------------------------------------------------

эмоциональный тезис.

# 18. SEO

Для индексируемых страниц: - title; - description; - canonical; -
OpenGraph; - robots; - sitemap.xml; - robots.txt.

Автоматически: - canonical для статьи/страницы; - schema.org
BreadcrumbList там, где применимо; - Article для статей; -
Organization/LocalBusiness --- только после согласования фактических
реквизитов и типа бизнеса.

Не публиковать фиктивные адреса, телефоны или реквизиты из макетов.

------------------------------------------------------------------------

# 19. Медиа

Требования: - изображения загружаются через админку; - генерировать
оптимизированные варианты; - WebP/AVIF при технической
целесообразности; - lazy loading ниже первого экрана; - hero/LCP
изображения не lazy; - alt редактируемый; - не использовать оригиналы
огромного размера непосредственно на frontend; - учитывать отдельные
изображения/кадрирование для mobile.

------------------------------------------------------------------------

# 20. Адаптивность

Текущий дизайн содержит desktop и отдельные mobile-состояния, особенно
для генплана.

Проверять минимум: - 360; - 390; - 768; - 1024; - 1280; - 1440+.

Не делать mobile простым пропорциональным уменьшением desktop. Следовать
мобильным композициям макета.

------------------------------------------------------------------------

# 21. Производительность

Цели: - минимизировать JS; - SSR/Blade для основного контента; -
responsive images; - кешировать публичные настройки и меню; - eager
loading без N+1; - индексы БД для
slug/status/published_at/category/status участка; - генплан не должен
загружать тяжелые данные, которые не нужны текущему уровню; - API
генплана должен позволять подгружать детали квартала/участков по
требованию.

------------------------------------------------------------------------

# 22. Безопасность

-   CSRF;
-   XSS-safe rendering;
-   HTML контент разрешать только через контролируемый
    редактор/санитизацию;
-   rate limit форм;
-   Policies для административных ресурсов;
-   audit-friendly timestamps;
-   запрет публичного доступа к неопубликованному контенту;
-   загрузки проверять по MIME/размеру;
-   секреты только через `.env`;
-   `.env` не коммитить.

------------------------------------------------------------------------

# 23. Тесты

Минимум feature tests: - публичные страницы 200; - 404; -
публикация/черновик статьи; - фильтрация блога; - создание заявки; -
валидация заявки; - права ролей; - недоступность admin для
неавторизованного; - статусы участков; - получение данных квартала; -
unpublished/hidden entities не попадают на публичный frontend.

Для генплана дополнительно unit/feature тесты преобразования/валидации
координат и API.

------------------------------------------------------------------------

# 24. Что НЕ делать

-   Не использовать WordPress.
-   Не писать собственную админку с нуля.
-   Не делать SPA только ради SPA.
-   Не превращать главную в Elementor-подобный конструктор.
-   Не хранить контент главной целиком одним HTML-полем.
-   Не хардкодить контакты в нескольких шаблонах.
-   Не хардкодить участки в JavaScript.
-   Не хранить позиции маркеров только в CSS.
-   Не реализовывать генплан одним большим JS-файлом.
-   Не придумывать отсутствующие в макетах страницы без согласования.
-   Не менять дизайн «на свое усмотрение».

------------------------------------------------------------------------

# 26. API генплана

Даже если frontend Blade-based, интерактивной части предусмотреть JSON
endpoints.

Примерно:

``` text
GET /api/genplan
GET /api/genplan/quarters/{quarter}
GET /api/genplan/quarters/{quarter}/plots
GET /api/genplan/plots/{plot}
GET /api/genplan/infrastructure
GET /api/genplan/surroundings
```

Реальные маршруты можно скорректировать. Ответы должны быть Resource/DTO
based, а не `Model::toArray()` без контроля.

# 28. Definition of Done для каждого релиза

Релиз не считается завершенным, пока: 1. миграции применяются на чистой
БД; 2. rollback не ломает проект; 3. тесты проходят; 4. нет N+1 в
основных сценариях; 5. frontend проверен desktop/mobile; 6. нет ошибок
console; 7. нет секретов в git; 8. права админки проверены; 9.
форматирование/lint проходят; 10. документация обновлена.

------------------------------------------------------------------------

# 29. Первое задание Codex

Перед написанием функционала:

1.  Изучить этот SPEC.
2.  Изучить все предоставленные макеты/экспорты.
3.  Проинспектировать существующий репозиторий, если он уже создан.
4.  Не начинать массовую генерацию кода до фиксации:
    -   версии Laravel;
    -   версии PHP;
    -   версии Filament;
    -   выбранного frontend CSS подхода;
    -   выбранного editor/content-block подхода;
    -   структуры ролей.
5.  Сформировать короткий implementation plan Release 0.
6.  Отметить вопросы/противоречия, которые реально блокируют разработку.
7.  После подтверждения выполнить Release 0 небольшими проверяемыми
    шагами.

# 30. Неопределенности, которые пока НЕ блокируют старт

Можно начать проект без окончательного решения по: - финальному UI
выбора конкретного участка; - конкретному провайдеру карты окружения; -
окончательному набору категорий POI; - реальным телефонам/адресам; -
окончательным текстам; - CRM-интеграции; - внешней телефонии; -
email/SMS провайдеру.

Для них должны быть предусмотрены точки расширения, но не нужно заранее
строить сложные абстракции.
